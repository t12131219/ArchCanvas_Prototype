# 通用项目源码边界扩充

目标：从原始项目的局部定义、导入和可证明构造关系展开模块，不依靠模型名、名称相似度或运行猜测。原始源码只读；CPU 观测仍是独立证据。

实施顺序：

1. 有界项目源码解析器，处理相对导入、绝对项目导入及重导出；按文件隔离名称空间，记录来源摘要。项目根和文件预算限制读取范围，循环、歧义及动态重绑定不误解析。
2. 保留 forward 默认行为；显式定义的 __call__ 优先于框架 forward，保留真实入口名称及未知边界。
3. 扩充无执行的构造解释：局部赋值、参数绑定、模块引用传递及小型工厂；拒绝不支持的副作用及动态路径。可选择工厂入口，但不执行工厂。
4. 扩充常见框架原语契约，并明确这是框架操作边界，不是已经读取其内部源码。
5. 独立多文件正反例、别名/同名/导入循环/副作用/动态条件/共享对象验证；冻结实现后重新捕获 ACT 和现有回归。原始 IR、源码归属、精确操作数及保存机制继续保留。

不把所有 opaque 消除作为通过条件。动态 getattr、反射、第三方 C/CUDA、自定义修改以及不确定工厂不能仅靠操作名称认定语义；需要保留原因和来源。

实施前备份：`/tmp/archcanvas-project-boundaries-20261027/before.tar.gz`。

## 已实现的边界

- `project.py`：在指定根目录内惰性读取 `.py` 源码。支持相对/绝对导入、模块别名、包重导出及命名空间包中的源码文件。不同文件的类名、框架别名和全局常量独立解析；返回证据仍指向原始物理文件。
- `analyzer.py`：类显式定义的 `__call__` 优先于 `forward`，与 Python 的实际调度次序一致；被装饰的可调用体继续保留未知边界。项目中的本地 `torch`/`math` 不获得外部库的操作契约。
- `construction.py`：支持有界的无执行工厂语言：局部单目标赋值、返回、可静态决定的布尔分支。跨文件构造参数可携带模块与模块集合引用；保留共享对象身份及各次调用。支持位置参数、仅位置参数、仅关键字参数；默认值从定义文件读取。对象型默认值不当作每次调用的新对象。
- 固定索引的 `ModuleList`、固定字符串键的 `ModuleDict` 可选出模块；动态索引保持边界。输入对象、集合修改和所有者逃逸仍受失效规则限制。字面名称的框架 buffer/parameter 注册不再使无关模块身份失效，名称碰撞会失效对应对象。
- 构造条件必须可证明；此前只在某个不确定构造分支中出现的模块，不能通过扫描到一个赋值就当作必然存在。本轮因此修正了一部分原有的过度展开，未知计数不保证单调下降。
- 常见 PyTorch 操作表从 37 到 113 个模块名称、86 到 160 个函数/方法名称。包括 RMSNorm、更多维度的卷积/池化、padding、dropout、repeat/full 等。它们表示框架 API 操作边界，不表示已经解析 C++/CUDA 内部实现，也不表示形状兼容性或运行覆盖证明。函数名称受明确的框架命名空间或既有接收者规则约束；未知类不凭短名称匹配。
- 项目模式中的未知调用增加 `unknown_boundary`，区分条件构造、注入对象和外部/动态目标，并保留源码位置、调用名和操作数。

## 使用

原有单文件接口与既有 IR/图文档格式保持兼容。未明确给项目根时，从入口文件的父目录及常规包目录推导有限根；跨命名空间包或更大项目请显式指定根。

```sh
python3 -m semantic_adapter.cli inventory --root /path/to/project --output /tmp/inventory.json
python3 -m semantic_adapter.cli analyze --source /path/to/project/model.py --entry Model --project-root /path/to/project --output /tmp/model.json
```

显式工厂入口（只解释支持的静态子集，返回项目中定义的模型类）：

```sh
python3 -m semantic_adapter.cli analyze --source tests/semantic_fixtures/project_imports/entry.py --entry build --factory --project-root tests/semantic_fixtures/project_imports --output /tmp/factory.json
```

`--constructor` 此时是该工厂的显式 JSON 参数。不会按工厂名称推断配置，也不执行 argparse、下载或设备迁移。`--factory` 目前仅用于静态分析，与 CPU 探针组合会明确报错；已有 CPU 类入口与输入规格流程保持不变。`--source-root` 在 CPU 场景也可作为静态项目根，显式 `--project-root` 优先。

浏览器仍通过“打开 IR / 图文档”载入生成的 JSON。此次没有新增浏览器项目目录选择器，没有批量重写已登记的 43 个 IR，也没有宣称已有目录自动获得重新解析结果。

## 证据与限制

独立正反例位于 `tests/test_project_boundaries.py`；持久化的独立多文件样例为 `tests/semantic_fixtures/project_imports/`。覆盖命名空间隔离、别名、重导出、关键字参数、默认值归属、对象共享、固定/动态索引、条件重绑定、装饰器、副作用、循环导入、源码只读、路径越界和文件预算等。

ACT 保持外部黑箱验收输入：使用原始文件、空构造参数和现有公共分析接口，没有重写入口，没有拼接文件，没有专用模型判断，也没有执行模型。最新扫描发现 15 个候选入口，全部 IR 格式/来源检查通过。`ACTPolicy` 从旧版 1 节点/0 边，扩展为 113 节点/132 边；画布初始切面为 24/34，来源、布局及路线检查通过。其核心 `self.model` 仍未知。

原始 `DETRVAE` 入口由 179/194 变为 177/192，仍有 17 个 opaque；重复/创建操作得到支持，同时不确定构造分支中的几个投影被更准确地保留为边界。不能将节点减少解释为覆盖增加。依赖外部配置、工厂副作用及对象注入的 encoder/transformer/backbone 尚未整体连接，本轮没有完成 ACT 全项目还原。其他 ACT 子入口的通过仅证明各自独立输入的提取结果有效，不能把分开的图视为已经组合成同一个 ACT 实例。

独立工厂样例为 8 个原始节点/6 条边，无 opaque；画布中间切面 7/4。共享 Linear 对象保留两个独立调用，完整来源及图文档几何往返通过。浏览器证据检查可查看各文件的源表达式与构造证据。

最新材料在 `verification/project-boundaries/current/`，旧 ACT 黑箱基线保留在 `verification/act-blackbox/current/`。`extraction-report.json` 记录原始项目摘要与捕获期间生产/测试冻结结果，`native-integration.json` 记录保存往返；截图和浏览器 DOM 检查独立保存。此次不声称 ACT 全展开的旧路线缺陷已经修复。

最终全量回归为 108 组、1223 项（其中 Python 162 项），所有命令退出码为 0。回归记录的 308 个实现/测试摘要和外部捕获记录的 301 个摘要在完成后复核一致。新增边界测试 20 项；ACT 源码保持不变。未提交、未推送。

## CPU 探针辅助未知边界

已有可选探针可以在显式解释器、构造参数和有效输入样例下，记录实际模块类型与调用、底层算子、张量生产/消费以及已执行条件结果。适合补充静态无法确定的对象注入和动态调用；不意味着已经解析原生算子内部实现。当前合并流程保留独立运行证据，不会仅凭源码行相同就消除静态未知节点；源码行关联不是算子等价证明。

现已在通用原生画布增加显式的“使用 CPU 探针进行辅助确认”，配置、边界关联、载入与保存方式见 [CPU 补证功能](cpu-probe-assistance.md)。目前仍没有自动为未知边界启动探针、生成输入或探索未覆盖分支的回退机制。未执行路径保留未知状态。ACT 未运行探针，没有为了运行而修改其源码、编写专用包装器或猜测配置。补证保留具体输入、模式、调用身份及覆盖范围，并将运行证据与静态证据分开展示。

当前预算为 128 个项目源码文件、32 层导入查找、8 层工厂递归、16 个有界模块集合元素，以及既有的 8000 节点/12 层调用深度。达到预算保持诊断或未知边界。任意继承/元类、动态属性、星号参数、未知构造条件、复杂工厂副作用、动态集合、第三方原生算子与自动分支探索仍不在已兑现范围。
